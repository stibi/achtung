# 0005: Ingest creates channels, the server migrates its own database

- Status: accepted
- Date: 2026-11-07

## Context

The first ingest path needs answers to three questions that shape how Achtung is run:
where channels come from, when database migrations run, and whether raw webhook
payloads are kept. Achtung is meant to be easy to self-host, runs on Kubernetes as one
image, and may run as several replicas behind an ingress.

## Decision

- **Channels are created on their first notification.** Pointing an Alertmanager
  receiver at `/ingest/alertmanager/<name>` is the whole setup; there is no channel
  configuration in Achtung. Names must match `^[a-z0-9][a-z0-9-]{0,62}$`.
- **The server applies pending migrations at startup**, holding a Postgres advisory lock
  so that replicas starting at the same time migrate one after another. No separate Job
  or init container is needed. Migrations are SQL files generated by drizzle-kit and
  committed in `server/drizzle/`.
- **Raw payloads are not stored.** Alertmanager resends every firing alert each
  `repeat_interval`, so stored payloads grow without bound until there is a retention
  policy. A payload that fails to parse is logged with its body instead.

## Consequences

- A typo in a receiver URL silently creates a stray channel. Renaming or deleting
  channels will need an API later.
- Migrations must stay compatible with the previous release while a rolling update runs
  both versions. Destructive changes need two releases.
- The database user needs DDL rights on its schema.
- Debugging a mapping problem relies on the logs of invalid payloads, or on capturing a
  payload by hand. This is revisited together with retention (see the README's open
  questions).
